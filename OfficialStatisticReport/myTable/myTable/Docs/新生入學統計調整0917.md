## 2. 原始慢速流程分析

主要瓶頸（優化前）：

1. **N+1 `BeforeEnrollment.SelectByStudentID(id)`**  
   在 `foreach (DataRow row in dt.Rows)` 內逐列呼叫。SQL 因 `tag_student`／`update_record_info` 一對多而膨脹列數，同一學生可能被查詢數次。
2. **重複學生物件層級工作**  
   即使最終以 `myDic[id]` 合併，每列仍可能做 BeforeEnrollment／地址 XML 解析。
3. **`CheckStudentStatus` 全表掃描**  
   每位學生都掃完整份 `UpdateRecord` 清單 → 接近 students × update records。
4. **`WriteDepartmentSheet` 的 `recl × summary` 巢狀迴圈**  
   O(n²) 學生對應。
5. **`CheckStudentBeforeStatus` 同一學生最多呼叫 3 次**  
   每次再掃異動清單。
6. **原住民清單在 `foreach (rec)` 內重複計算**  
   `filter.getListByTagId(aboIDList, summary)` 與 `rec` 無關卻每筆重算。

## 4. BeforeEnrollment N+1 問題與解法

### 問題

```csharp
K12.Data.BeforeEnrollment.SelectByStudentID(id); // 每 DataRow 一次
```

呼叫次數約等於 SQL 列數（常遠大於唯一學生數）。

### 解法

使用既有批次 API：

```csharp
K12.Data.BeforeEnrollment.SelectByStudentIDs(myDic.Keys.ToList());
```

建 `Dictionary<StudentID, SchoolLocation>` 後回填 `myStudent.Before_School_Location`。

預期：

```text
BeforeEnrollment batch calls = 1
BeforeEnrollment query 不再等於 SQL row count
```

---

## 5. 重複 DataRow 優化

`foreach (DataRow row)` 內：

- **僅當 `!myDic.ContainsKey(id)`**：建立學生物件、解析戶籍地址 XML
- **每列**：`myDic[id].Tag.Add(ref_tag_id)`

同一學生多個 Tag 列仍會正確累積全部 Tag。

---

## 6. 新生狀態 HashSet 優化

原：

```csharp
if (CheckStudentStatus(records, kvp.Key)) mylist.Add(...);
```

現：

```csharp
HashSet<string> validNewStudentIds;
// SchoolYear == _SchoolYear && UpdateCode < 100 → Add(StudentID)
if (validNewStudentIds.Contains(kvp.Key)) mylist.Add(...);
```

業務規則不變；`CheckStudentStatus()` 方法仍保留（未刪除）。

---

## 7. `recl × summary` 巢狀迴圈優化

建：

```csharp
Dictionary<string, myStudent> summaryById
```

改：

```csharp
if (!summaryById.TryGetValue(rec.RefStudentID, out student)) continue;
```

畢／修業判斷規則不變。

## 8. `CheckStudentBeforeStatus` 快取

預先建立：

```csharp
Dictionary<string, string> studentBeforeStatusMap
```

每位學生只呼叫一次 `CheckStudentBeforeStatus`，結果值仍為：

- 當年畢業
- 當年修業
- 其他(含領結業證書)

`aboStudentlist = filter.getListByTagId(aboIDList, summary)` 移到 `foreach (rec)` **之外**，並建 `aboById` 做 O(1) 查找。

# 部別人數統計方式調整（2025/09/17 同日追加）

## 1. 修改檔案

- `Filter.cs`
  - 新增 `GetReportDeptGroupName()`：資料庫部別名稱 → 報表工作表名稱
  - `Cleaner()`：先轉換再驗證；有效學生寫回正規化後的 `Dept_group_name`
  - `Classify()` 後輸出各工作表人數診斷 log
- `Form2.cs`
  - Filter 建立後補記 `clean_list`／各部別 students 至效能 log

未修改：

- SQL 科別解析（`ref_dept_id` 優先／班級 fallback）
- `getClassCount`／`getGenderCount`／`getListByTagId`
- 入學方式／入學身分／Tag／班別對照
- 報表工作表名稱與版面

---

## 2. 根本原因

資料庫 `dept_group.name` 與 Excel 報表工作表名稱使用不同命名體系：

| 資料庫 | 報表工作表 |
|--------|------------|
| 普通型高中 | 普通科 |
| 技術型高中 | 專業群科(職業科) |

舊邏輯假設兩者相等，導致 `IsSupportedDeptGroup()` 誤判。

---

## 3. 原錯誤行為

`Cleaner()` 直接以原始 `s.Dept_group_name` 比對 `SupportedDeptGroupNames`（報表名稱）：

```text
普通型高中 != 普通科
技術型高中 != 專業群科(職業科)
```

有效學生被放入 `error_list`，無法進入正確工作表統計。

---

## 4. 新部別對應邏輯

集中於 `GetReportDeptGroupName()`，精確比對（允許 `Trim()`），不使用 `Contains()`：

```text
普通型高中 / 普通科          -> 普通科
技術型高中 / 專業群科(職業科) -> 專業群科(職業科)
綜合高中                     -> 綜合高中
實用技能學程                 -> 實用技能學程
進修部(學校)                 -> 進修部(學校)
其他／空白                   -> ""（異常）
```

未知別名不猜測；確認實際 DB 值後再擴充對應。

---

## 5. Cleaner 驗證變更

流程：

```text
讀取 DB Dept_group_name
    ↓
GetReportDeptGroupName(...)
    ↓
以 reportDeptGroupName 是否為空判斷可否歸類
    ↓
通過：s.Dept_group_name = reportDeptGroupName → clean_list
失敗：error_list（不改寫 Dept_name／Dept_code／Class_Type）
```

`SupportedDeptGroupNames` 仍維持報表工作表名稱，供 `Form2.Export()` 迴圈使用。

---

## 6. Classify 行為（正規化後）

因 `clean_list` 內 `Dept_group_name` 已是報表名稱，`Classify()` 可繼續：

```csharp
ByDeptGroup[s.Dept_group_name]
```

再由 `GetSortedGroups(sheetName)` 寫入對應 Excel 工作表，無需改工作表名稱。

---

## 7. 異常資料行為

下列仍進 `error_list` → `異常資料表`：

- `Dept_name` 空白
- `Dept_code` 空白
- 部別無法對應（`GetReportDeptGroupName` 回傳空字串）
- 其他既有欄位／班別異常條件

不強制推測部別。

